# General Decisions
Decision made here and onward are **set in stone**. Design new features around these restrictions.
Accept that some features _cannot be implemented_ under these restrictions and that is fine for a hobby project.
Only change, when there is really no other possibility at all and consider consequences for the entire language.

1. **Type System**
   * **Value Types** - Types with *no observable identity*: Immutable (shallow), structural equality.
     * Assignment may copy or alias (not distinguishable)
     * Compiler can freely choose memory layout (inlined or boxed)
     * Compiler can freely choose how to share (copy or alias)
     * Stricter than C#'s value type (only requires copy on assign); closer to Java Valhalla value objects.
     * *Axls value types:* Primitives, char, string, `value record`, `enum`
   * **Reference Types** - Assignment *aliases*
     * Default equality: identity. Opt-in structural
     * Mutable
     * *Axls reference types:* `ref record`, array `T[]`, `class`
   * **Shallow immutability** - All immutability promises are shallow, never transitive/deep
       * This will create footguns, but its a concession to make implementation and rules (much) easier.
   * **Object identity is not explicitly queryable** - That would break the value type contract.
     * Equality is always structural or implicitly identity for reference types

   * Invariant type relation; no subtyping
     * Centralized as a `bool Assignable(Type target, Type source) => target == source;` function
     * Note: Classes with inheritance will break that. If I ever want to implement classes, that will be a rewrite.
   * No implicit conversion; no number widening
   * No default values; No _null_
2. **Error Handling**
   * Panic for crashes
     * Triggered through native function. 
     * Stack-Trace from own stack frame
     * Cannot be caught => _no_ try/catch instructions
   * Expected error propagation through `Result` and `Maybe` (see below)
3. **Pipeline**
[Syntax] ──bind──► [HIR] ──lower──► [MIR<Generic>] ──analyze──► [MIR<Generic>]
                                         │
                                     monomorphize
                                         ▼
                                     [MIR<Concrete>] ──optimize──► [MIR<Concrete>]
                                     │            │
                                  codegen         │
                                     ▼           ▼
                                 [ByteCode] | [MirInterpreter]
                                     │
                                     ▼
                                    [VM]

   * *Query style*: Compilation, DeclarationTable, SemanticModel answer questions about code
     * Same question => always same answer. Query objects lazily retrieves that information from IRs (and caches)
   * *SyntaxTree*: lossless, spans recreate source text completely, carries all trivia; feeds Binding, Formatting
   * *HIR*: Follows syntax closely (no desugaring), types and names resolved; feeds Lsp, Lowering
   * *MIR*: Register-based, three-adress-code, CFG, carries type information and syntax references. 2 Phases:
     * _Generic_: has type parameters; feeds CFG passes with diagnostics, e.g. definite assignment
     * _Concrete_: no type parameters, result of monomorphization. feeds optimization, MirInterpreter, codegen. No diagnostics.
   * *ByteCode*: Register-based, optimized for fast runtime. CodeGen and VM(+GC) is an optional coding adventure.

# Features and Decisions
This is a loose list of features that can or cannot be implemented as I see fit and feel like
doing it. This list provides an overview over what the language could look like and records decisions 
that have been made about these features.

* **Expression-Based**
  * basic expressions (numeric, comparison, equality, boolean)
    * Integral operations are _unchecked_ and _wrapped_ following C# behaviour. `i32.MinValue / -1` panics.
    * Numeric (i32, i64, f32, f64): +, -, *, /, unary -
    * Comparison (i32, i64, f32, f64): <, <=, >, >=
    * Equality (all): ==, !=
    * Boolean (bool): not, and, or  (!! `and, or` do control flow)
    * Later: Behavior for comparison & equality can go through traits
  * blocks, if, loop are expressions
* **Variables**
  * Mutable bindings, except parameters & iteration variables are immutable bindings
  * Full shadowing allowed
  * Initializers required
    * optional coding adventure: make optional with definite assignment  (captures need definite assignment)
  * Types inferred locally
* **Basic types**:
  * Primitives: i32, i64, bool; f32, f64 implement full specification
  * Literal types inferred by expected type propagation
  * char (32-bit full unicode character; no surrogates)
  * None and Never
* **Strings**
  * value type, immutable with structural equality
  * with Formatting and Escapes
  * Not indexable
  * Characters available as iterator through `.Characters()`
  * UTF-16 for start. The above make switch to UTF-8 possible.
* **Arrays**
  * ref type, mutable
  * emits to Mir instruction directly
  * Provides base for Axl implementations of List, Map, ...
  * Creation only through Array expressions (default must be specified)
* **Standard Library**
  * Print, PrintLine
  * ToString
  * Panic (graceful crash with error message)

* **Functions**
  * Hoisted, mutual recursion and call-before-declaration is possible
    * For captures (later) this requires definite assignment
  * Overloadable by type
  * Expected type propagation may be restricted for overloaded functions (don't overdo it)
* **Native Functions**
  * Defined in axl code and map to runtime equivalent trough stringed name
  * Runtime implementation takes raw ReadOnlySpan<Value> input and does bounds checks itself
  * Debugging: Compiler has a map Name -> Signature to provide meaningful error messages
* **First-Class Functions, Captured Variables & Lambdas**
  * Functions can capture variables
    * This will require definite assignment for hoisted functions
  * Functions can be values in most places
  * Lambda expressions, type can be inferred by expected argument type (not/restricted for overloaded functions)

* **Modules**
  * Multiple files
  * Script and module files
  * Visibility: default private, opt-in `public`
  * `private` may be written to be explicit
  * Name aliasing through `using`

* **Ref Records**
  * product type; reference type
  * 0-sized ref records possible: `ref record RefUnit;`
    * different from 0-sized `value record ValueUnit;`
    * `RefUnit() == RefUnit()` is false (different identity)
    * `ValueUnit() == ValueUnit()` is true (structural equality)
* **Value Records**
  * product type
  * value type (see Type System) =>
    * immutable (shallow), structural equality (on fields)
    * Compiler chooses memory representation (inline or boxed) and assignment behaviour
  * Any type is allowed as field. Promise of value type is kept through its shallow immutability.
  * 0-sized value records possible (just like none type): `value record Unit;`
* **Enums**
  * sum type: tagged discriminated union
  * value type (see Type System) => 
    * immutable (shallow), structural equality (on tag + payload)
    * Compiler chooses memory representation (inline or boxed) and assignment behaviour
* **Generics and Traits**
  * Generics are monomorphized, invariant, trait-bound. If implemented, classes can use runtime polymorphism.
  * Type parameters flow into generic phase of Mir
  * Traits for equality, hashes, to string conversion can override default behaviour
  * Parser resolves syntax ambiguity between generic `f<i32>(x)` vs comparison `a < b > (c)`
  * _No_ dyn Trait/fat pointers. Use classes later instead.
  * Type parameter inference is optional coding adventure
  * Trait derivation is optional coding adventure
* **Extensions**
  * Extensions are globally visible. Do not depend on usings/imports.
  * Private members are _not_ visible to extensions blocks.

* **Iterators, Collections**
  * Traits for collections and iterables
  * `for` loop
  * Standard implementations of list, map, set
  * Extends array expressions into collection expressions, including spread operator and slicing
  * Fluent api on iterables (map, select, where, ...)
    * Iteratable trait implemented on custom `value record` (no dyn traits)
* **Patterns**
  * Tuples
  * Positional Patterns, Destructuring Patterns
  * Exhaustive Match on enums
* **Error Handling**
  * `Result<T, TError>` and `Maybe<T>`
  * Error propagation syntax

* **Generator Functions/Loops**
  * Generator functions and for loops (through `yield`)

* **Classes**
  * reference type with inheritance and runtime polymorphism
  * Only, if I ever want to engage with it.
  * requires rewrite of Type System, since until that point, it does not allow subtyping

  * V-Tables
  * Abstract base classes
